## Project Overview

A Roblox idle/farming/merging game written in Luau. Players fuse (merge) dragon eggs, crops,
crystals, gems, packs and keys on island plots to progress. The Rojo project and the wally package
are both named `md` ("Marge those Dargons!"); the player-facing brand is "Fuse Dragons". Note that
what players call **fuse** is called **merge** everywhere in code (`MergeMixin`,
`ClientMergeController`, `Tags.MERGEABLE`) — the word "fuse" only appears in display strings.

## Development Setup

```bash
foreman install      # Install pinned rojo 7.7.0, wally 0.3.2, wally-package-types 1.6.2
wally install        # Install iris + topbarplus into Packages/
rojo plugin install  # Install the Rojo plugin into Roblox Studio
rojo serve           # Sync src/ into Studio; run this while editing
rojo sourcemap analysis.project.json --output sourcemap.json  # Refresh sourcemap for luau-lsp
```

There is no build step, no test framework, and no linter/formatter config. Verification means
running the place in Studio. `sourcemap.json` is checked in and consumed by luau-lsp.

`analysis.project.json` is an analysis-only copy of `default.project.json` that additionally maps
`ServerScriptService.GameData` to `src/GameData/` (a pulled-in copy of the Studio-side GameData) so
luau-lsp can resolve GameData requires. `rojo serve` still uses `default.project.json`, so
`src/GameData/` is never synced into Studio.

All of `src/shared` and `src/server` is `--!strict`. Analyze with
`luau-lsp analyze --defs=<globalTypes> --sourcemap=sourcemap.json src/shared src/server`; expect
**zero** diagnostics in `src/` (vendored `ServerLibs/ProfileStore` reports pre-existing errors of
its own, which are out of scope).

`src/client/Version.luau` is gitignored and generated by a post-commit hook that writes the current
commit SHA. `main.client.luau` requires it, so the client will not boot without it. **A fresh clone
has no such hook installed and no Version.luau** — create one (`return { commit = "..." }`) if the
client fails to start.

## Out of Scope

Do not modify or analyze `ClientLibs/` (ParticleEmitter, Rain, Satchel), `ServerLibs/`
(ProfileStore), `Packages/` (wally output), or `src/plugin/` (a Studio-only authoring plugin built
from `plugin.project.json`). Assume the vendored libraries work as named.

## The Studio-Side Half of the Codebase

This is the single most important thing to understand: **a large amount of what the code depends on
does not live in this repo.** It is authored as Instances inside the Roblox place file and is not
synced by Rojo.

| Studio location | Contains | Consumed by |
|---|---|---|
| `ServerScriptService.GameData.Objects` | One ModuleScript per item/object definition (`name`, `type`, `mixins`, `templatePath`, `boardSpacing`, …) | `ObjectDataStore:initDataTypes()` |
| `ServerScriptService.GameData.Control.*` | Balance/tuning tables — `Progression`, `Capacity`, `Luck`, `Mutations`, `Modifications`, `AbilityValues`, `CrystalTime`, `EatingTime`, `OfflineHarvesting`, `Nodes`, `Codes`, `Start`, `StarterOffer`, `FirstSessionOffer`, `IndexChainRewards`, `VanityAreas` | `require("@game/ServerScriptService/GameData/Control/X")`, ~53 call sites |
| `ServerScriptService.GameData.LootTables` | One ModuleScript per loot table | `LootTableManager:init()` |
| `ServerScriptService.GameData.Vanity` | `MainPlotInner`, `MainPlotOuter`, `Fence`, `ExpansionInner`, … | `PlotsManager:initVanityData()` |
| `ReplicatedStorage.RemoteEvents` | Every RemoteEvent instance | server + client (see below) |
| `ReplicatedStorage.GameAssets` | Model templates, particle effects, audio, gnomes | `utils.getGameAssetPathReference(path)` |
| `workspace.Level` | Plot geometry, merge plot, cloned plot elements | `PlotsManager`, `PlayerData` |

Consequences:

- **No code in `src/` creates a RemoteEvent.** Adding a new remote requires creating the Instance
  under `ReplicatedStorage.RemoteEvents` in Studio *and* wiring it in `GameController:listenToRemoteEvents()`.
- Adding a new item means adding a GameData ModuleScript and a GameAssets template in Studio, not
  just code here.
- `sourcemap.json` does not cover `GameData`, so luau-lsp cannot resolve those requires. Expect
  unresolved-module noise there; it is not a real error.
- `GameDataVerifier` runs at startup and `warn()`s about malformed GameData (missing asset paths,
  bad loot-table shapes, unknown item names). Check the output console when data-driven things break.

## Require Conventions

Luau require-by-string throughout. There is no `.luaurc`; aliases resolve against the DataModel.

```lua
local Item = require("./Item")                                    -- sibling within the same realm
local ProfileStore = require("./Libs/ProfileStore")               -- vendored lib under the realm
local utils = require("@game/ReplicatedStorage/Shared/utils")     -- shared code, from any realm
local progressionData = require("@game/ServerScriptService/GameData/Control/Progression")
```

Requires are kept alphabetized in three blocks: Roblox services and Instance lookups, then
`@game/...` shared/GameData modules, then local `./` modules.

## Module Lifecycle Pattern

Nearly every module is a singleton class:

```lua
local Foo = {}
Foo.__index = Foo
local Types = require("./Types")
local bar: Types.Bar -- injected via initClass(deps); typed through Types.luau to avoid the require cycle
function Foo.new() ... end        -- pure construction, runs at require time
function Foo.initClass(deps: any) bar = deps.bar end  -- receive deferred singletons (no requires here!)
function Foo:init() ... end       -- real startup work; may touch other modules
local singleton = Foo.new()
return singleton
```

Three phases, in order: **module scope** (`.new()`, no cross-module calls) → **`initClass(deps)`**
(receive deferred singletons) → **`init()`** (startup). Injection is reserved for dependencies that
would make the static require graph cyclic — the back-edges to `gameController` and `itemManager`
(which statically require everything / all item classes), plus `islandManager` in Validate and the
store managers in Crate; those are the only keys in the `deps` table. Everything acyclic is a plain
top-level require — do not add a dep to `deps`/`initClass` unless a top-level require would create a
cycle. A module that needs an injected dep declares it as an uninitialized local typed through
`src/server/Types.luau` (see below) and assigns it in `initClass(deps)` (built in
`GameController.initClasses`, which owns the canonical hand-ordered call list). initClass bodies
must NOT require() other server modules — that is what previously made the static require graph
cyclic and drowned luau-lsp in "Cyclic module dependency" errors; the module-scope require graph is
acyclic and must stay that way. ~35 server modules follow this pattern; breaking the ordering causes
silent nil-index crashes at boot.

### Types.luau: typed injection without requires

Each realm has a central type module — `src/server/Types.luau` and `src/client/Types.luau` — for
every type used across module boundaries in that realm; neither may require another module of its
realm. Each has two sections:

- **Hand-maintained (top)**: on the server, the class-hierarchy interfaces (see "How the class
  hierarchies are typed") plus small cross-module types (`Timer`, `Repulsor`, `DubinsPlan`,
  crop/crystal state records); on the client, the `Overlay`/`OverlayNotifier` protocols and
  `PartMap`.
- **Generated (below the marker)**: written by `tools/generate_types.py` (optionally
  `server`/`client` as an argument) — a methods-only interface for each initClass-injected
  singleton (plus `PlayerData` on the server), derived from the annotated
  `function X.name(self: X, ...): R` definitions in the source files.

Because Types.luau requires no server modules, any file can require it for annotations without
recreating the cycles that dependency injection removed. The injected values still arrive untyped
through `initClass(deps: any)`, so the generated interfaces are a promise, not a checked contract:
**after changing any method signature on an injected singleton or PlayerData, re-run
`python3 tools/generate_types.py` and then the luau-lsp analysis.** The generator preserves the
hand-maintained section, allows `Types.Foo` references in signatures (the qualifier drops away
inside the file), and refuses to emit a signature that would force Types.luau to require a server
module.

Cross-module code is typed against these interfaces: `itemManager:getItemById(id)` returns
`Types.Item?` (nil-guard it, or use a documented `:: Types.Item` cast when a preceding Validate call
guarantees existence), `createItem`/`cloneItem` return `Types.Item?`, the list getters return typed
arrays (`{ Types.ShadowDragon }`, `{ Types.Crop }`, …), and narrowing an Item to a subclass after a
`getType()` check is a typed downcast (`local crop = item :: Types.Crop`). Reserve `any` for what is
genuinely dynamic: untrusted client arguments in `Try*` handlers, GameData/save-data tables, and
item `obj`/`part` instances.

- **Server boot:** `src/server/init.server.luau` → `GameController`. Its module scope builds the
  singleton, then a `coroutine.wrap` runs `initClasses()`, which does `task.wait()` (letting all
  module scopes finish), calls `initClass()` on ~35 modules in a hand-ordered list, then
  `gameController:init()`.
- **Client boot:** `main.client.luau` requires ~55 managers, calls `initClasses()` (its local deps
  table + `X.initClass(deps)` on the ~23 modules that used to lazily require each other inside
  `init()` — those in-function requires are what made luau-lsp's client module graph cyclic and are
  banned now, same as on the server), then calls `:init()` on the managers in a hand-ordered
  sequence. `ClientEventHandlers:init()` is last. Because `NotifyInit` can arrive before
  that, `ClientEventHandlers` connects to it at *module* scope and buffers `initData` for replay.

## Client–Server Communication

All traffic goes through `ReplicatedStorage.RemoteEvents` (~112 events). Naming is strict:

- `Try*` — client → server request (`TryPickupItem`, `TryMergeItemsWithHeldItem`, `TryBuyItemName`)
- `Notify*` — server → client (`NotifyInit`, `NotifyPickupStatus`, `NotifyMergeEnd`)

Server side, `GameController:addRemoteEventHandler(remoteEventName, methodName)` connects
`OnServerEvent` to `self[methodName]` and records per-event call count and elapsed time in
`remoteEventMetrics` (surfaced via `ClientNetopsTools`). Every handler is a `GameController` method
that **must** validate its arguments first — see `Validate.luau`
(`isItemIdForPlayer`, `areItemIdsForPlayer`, `isPlayerHoldingItemId`, `isTableShape`,
`isPlayerNameOnServer`, …) plus `Abilities.validateAbility`, `enums.validateValue`,
`FtueSteps.validateStepName`. Follow that pattern for any new handler; the client is untrusted.

Two non-remote channels also exist:

- **Attributes + CollectionService tags** carry most world state. The server sets Instance attributes
  (`src/shared/Attributes.luau`) and tags (`src/shared/Tags.luau`); client managers subscribe with
  `collectionService:GetInstanceAddedSignal(Tags.X)` and also sweep `GetTagged(Tags.X)` in `init()`
  to catch instances that already exist. These two shared files are the replication contract — treat
  a change to either as a cross-realm API change.
- **MessagingService** for cross-server work (`ServerListener` + `ServerTopics`), currently only
  `DISCONNECT_USER`.

Player currencies/stats go through `PlayerAttributesManager:set()`, which fires
`NotifyPlayerAttributeChange` per key; keys are in `src/shared/PlayerAttributeKeys.luau`.

## Object and Item Model

Two parallel hierarchies, both fed by data from `GameData/Objects`:

**Data types** (`DataType` → `ObjectType` → `CropObjectType`, `DragonEggObjectType`,
`CrystalObjectType`, `GemObjectType`, `PackObjectType`, `KeyObjectType`, `BlueprintObjectType`,
`CrateObjectType`, `ShadowDragonObjectType`, `NodeObjectType`, `ChestObjectType`,
`CritterObjectType`). `ObjectDataStore` walks `GameData.Objects`, dispatches on the `type` field via
`dataTypeClassMap`, shape-validates with `Validate.isTableShape`, and resolves `templatePath` into a
GameAssets Model. `ModificationDataStore` does the same for modifications.

**Runtime instances**:

- `Item` → `NumberItem` (stackable count, `splitOffOne`/`splitOffCount`) → `MItem` (mutations +
  modifications) → `Crop`, `DragonEgg`, `ShadowDragon`. Plain `NumberItem` subclasses: `Crystal`,
  `Gem`, `Pack`, `Key`, `Blueprint`, `Crate`.
- `BaseObject` → `Node`, `Chest`, `Critter` — world fixtures, not player inventory.

`ItemManager` is the registry (`itemTypeClassMap`, id allocation, `createItem`, `cloneItem`, lookup
by user/ground/type).

### How the class hierarchies are typed

Every class in the four hierarchies (Item family, BaseObject family, DataType family, ItemMover
family) has an interface-style type (plain table of fields + method signatures — deliberately
NOT `typeof(setmetatable(...))`, which the old solver treats as invariant across inheritance).
These interfaces **live in the hand-maintained section of `src/server/Types.luau`** (so they can be
referenced from anywhere, including the generated singleton interfaces); each class file re-exports
its own as an alias (`export type Crop = Types.Crop`). Subclass types compose by intersection and
list **only members new to that class**:

```lua
export type NumberItemFields = Item.ItemFields & { number: number }
export type NumberItem = Item.Item & {
	number: number,
	addCount: (self: NumberItem, count: number) -> (),
	-- ...new methods only
}
```

Rules that keep both solvers clean: never redeclare an inherited or overridden member in the child
type (the new solver rejects the resulting overload as ambiguous — the parent's declaration accepts
the child `self` because the intersection is a real subtype); super calls pass `self` directly with
no cast; constructors bridge the metatable with exactly one confined cast,
`(setmetatable(super.new(...), Child) :: any) :: Child` (parenthesized — `x :: any :: T` unchained
is a syntax error).

### Mixins are data-driven observers, not method injection

`MergeMixin`, `PickupMixin`, `RideMixin`, `SellMixin`, `VerticalMixin` are singletons registered in
`GameController`'s `mixinData` map and handed to `ItemManager.initMixins()`. An item opts in via its
GameData `mixins` table (e.g. `mixins.merge.mergeName`). `ItemManager:applyMixinsToItem()` then calls
`mixin:notifyItemCreated(item)` (or `notifyItemCloned`) for each declared mixin, and the mixin
applies attributes/tags/connections. Item classes check `self:getItemData().mixins.pickup` before
calling into a mixin. Nothing is copied onto the class metatable.

### Venues and settling

`Item` tracks a `Venues` state (`WORKSPACE_AVAILABLE`, `PLAYER`, `WORKSPACE_SETTLING`,
`WORKSPACE_BUSY`) plus per-type state enums (`DragonState`, `CropState`, `CrystalState`, `NodeState`,
…) in `src/shared/Enums.luau`. `Item:settleOnGroundInWorkspace()` implements the anti-overlap system:
it gathers every other ground item of the same owner as a "repulsor" weighted by that item's
`boardSpacing`, computes a final position, and tweens there. Items that must be placed exactly (load
from save, scripted spawns) call `setPreventSettling()` first.

### Movers

Item motion is pluggable: `ItemMover` → `CircleItemMover`, `DubinsItemMover` (with `Dubins.luau`
path math), `DirectFlyItemMover`, `PathfindingItemMover`, `UpAndOverItemMover`.

## Persistence

`ProfileStore` (session-locked) in the `playerProfiles` DataStore, keyed by userId string.
`GameController:tryStartProfileSession` opens the session; `profile.OnSave` writes
`profile.Data = { standardSave = playerData:getSaveData() }` — everything durable lives under that
one key. `PlayerData` (~3k lines) owns the in-memory state and `loadSaveData`/`getSaveData`.

`StorageManager` centralizes all DataStore names and key formats and holds the raw
load/save helpers for the non-ProfileStore stores (player options `s_<id>`, purchases `p_<id>`,
trade logs `t_<id>_<time>`, legacy pre-ProfileStore game saves `g<id>_<slot>`). There is a live
migration path from the pre-ProfileStore format in `GameController` player-join.

### Client typing conventions

All of `src/client` is `--!strict` and follows the same shape as the server: `XFields` type +
`export type X = typeof(setmetatable({} :: XFields, X))`, methods as
`function X.name(self: X, ...): R` (which is also what `tools/generate_types.py` parses). Specific
to the client:

- Overlays implement the `Types.Overlay` protocol and pass themselves to
  `overlayTracker:notifyBeginOverlay((self :: any) :: Types.Overlay)` — the metatable singleton
  type does not unify with the plain interface, so the documented any-bridge cast is the pattern
  (same for `Types.OverlayNotifier` and `addOverlayNotifier`).
- Studio-authored instances are the client's untyped boundary, always with a comment saying why:
  `local RemoteEvents: any = ...` ("the RemoteEvents children only exist in Studio"), gui roots and
  GameAssets templates as `: any`, character rig access via `(player.Character :: any)`, and
  world item/shadow/caster instances as `any` fields.
- `GetAttribute` on a *typed* `Instance` returns `unknown?` — cast at the read
  (`:: number`, `:: string`) when the value feeds arithmetic or formatting; `enums.getName` /
  `enums.getPublicName` return `string?` and usually need `:: string`.
- Connection results feeding `table.insert` on an `any`-typed callee must be hoisted into a
  `local x: RBXScriptConnection` first (an any-call's variadic return confuses the new solver's
  overload pick).
- `tools/convert_client_strict.py` was the mechanical first pass for this conversion and documents
  the transforms; new modules should just be written strict directly.

## Conventions Worth Matching

- All scripts live in this repo — never attach scripts to parts in Studio (per README).
- Tabs for indentation; `local` singletons in camelCase, classes in PascalCase.
- Failures are reported with `warn(message, ...context)` and an early return rather than raised
  errors; DataStore calls are wrapped in `pcall` and return `(isSuccess, value)`.
- Dated comments (`-- as of 2026-january-5 ...`) are used to record when an observation was made;
  follow that if adding one.
